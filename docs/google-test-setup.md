# GOOGLE TEST SETUP — solo localhost

Esta guía continúa desde `mock`. No copiar reservas mock a Google ni a Redis. No cambiar Vercel, dominio ni producción. `.env.local` ya existe y está ignorado por Git: editarlo directamente, sin pegar credenciales en el chat.

## LOCAL MOCK

`BOOKING_MODE=mock` y `BOOKING_STORAGE=local` conservan la agenda histórica en `.local/booking-agenda-mock.json`. Sus reservas no se sincronizan al entrar a Google TEST.

## GOOGLE TEST

1. En [Google Cloud Console](https://console.cloud.google.com/), crear o elegir un proyecto **de desarrollo**. Ir a **APIs y servicios → Biblioteca**, buscar **Google Calendar API** y pulsar **Habilitar**. La [guía oficial](https://developers.google.com/workspace/guides/enable-apis) confirma ese recorrido. No hace falta habilitar Google Meet REST API: Calendar crea la conferencia con `events.insert` y `conferenceDataVersion=1`.
2. En **Google Auth Platform → Branding / Audience**, completar el consentimiento para una prueba. Si el tipo es externo, mantenerlo en **Testing** y agregar solo la cuenta de Google que será dueña de los calendarios como test user. Google [documenta](https://developers.google.com/identity/protocols/oauth2) que un refresh token de una app externa en Testing puede caducar a los siete días.
3. En **Google Auth Platform → Clients → Create client**, elegir **Web application**. Agregar exactamente `http://127.0.0.1:4280/oauth/callback` a **Authorized redirect URIs**. Es el callback de `scripts/booking-oauth.mjs`, independiente del servidor `127.0.0.1:4174`. Los scopes son `https://www.googleapis.com/auth/calendar.events.owned` y `https://www.googleapis.com/auth/calendar.freebusy`: el primero permite leer, crear y borrar eventos en calendarios propios; el segundo consulta disponibilidad. [Google Events](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) y [FreeBusy](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query) aceptan esos scopes. La cuenta que autoriza debe ser dueña de ambos calendarios.
4. En Google Calendar, crear dos calendarios secundarios bajo esa misma cuenta: **Reac Test — Misael** y **Reac Test — Tomás**. En la configuración de cada uno, **Integrar calendario → ID de calendario**, copiar el ID a `GOOGLE_CALENDAR_ID_MISAEL` o `GOOGLE_CALENDAR_ID_TOMAS`. Deben ser distintos y no `primary`. Si ya existen calendarios dedicados a pruebas, reutilizarlos.
5. En [Upstash Console](https://console.upstash.com/), reutilizar una base **de desarrollo** si ya está disponible; crear una solo si no existe. En **Connect → REST** copiar URL y token a `UPSTASH_REDIS_REST_URL` y `UPSTASH_REDIS_REST_TOKEN` de `.env.local`. No usar una base de producción. [Referencia Upstash](https://upstash.com/docs/redis/features/restapi).
6. En `.env.local`, completar `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, los dos Calendar ID, `BOOKING_TEST_EMAILS` (solo cuentas propias de prueba separadas por comas), `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` y `CONTACT_RATE_LIMIT_SECRET` de al menos 32 caracteres. No modificar el secreto administrativo. `GOOGLE_CALENDAR_ID` global no reemplaza los dos IDs explícitos en este modo.
7. Ejecutar `node --env-file=.env.local scripts/booking-oauth.mjs`, abrir la URL que imprime y autorizar la cuenta de desarrollo. El helper escucha solo en `127.0.0.1:4280` durante cinco minutos, valida `state` y guarda `GOOGLE_REFRESH_TOKEN` directamente en `.env.local`; no muestra tokens ni crea eventos. La [documentación OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) exige que el redirect coincida exactamente.
8. Cuando todo esté completo, cambiar `.env.local` a `BOOKING_MODE=google_test` y `BOOKING_STORAGE=upstash`; reiniciar `npm run dev`. El modo falla cerrado si falta cualquiera de los calendarios, si coinciden, si se usa `primary`, si falta OAuth/Redis o si la allowlist es inválida. El build no incluye secretos.
9. Ejecutar `npm run booking:doctor` para ver nombres y estados sin llamadas externas. `npm run booking:doctor -- --probe` consulta **PING** de Upstash y FreeBusy real de ambos calendarios, sin escrituras ni eventos. El panel privado ofrece el mismo probe en **Configuración → Verificar configuración local**; exige sesión local. Los fallos muestran códigos cortos, sin tokens ni contenido de eventos.
10. Con un email autorizado, reservar una fecha futura a las 09:00 con Misael. Comprobar HTTP 200, calendario correcto, hora de Córdoba, fin, `[TEST]`, attendee, enlace Meet real y reserva en Upstash. Repetir con Tomás a la misma hora. Crear manualmente un bloqueo **solo de prueba** 11:00–12:00 en el calendario de Misael y comprobar que FreeBusy quita sus slots compatibles, incluidos buffers, mientras Tomás conserva los suyos. Nunca usar emails de clientes. `sendUpdates=none` limita notificaciones, pero Google [advierte](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) que algunos correos aún podrían enviarse.
11. Para limpiar **un** evento creado por esta app en GOOGLE TEST, conservar su UUID. Primero `npm run booking:test:cleanup -- --booking-id UUID`: es una lectura de prueba. Luego, si confirma el profesional y la marca de TEST, `npm run booking:test:cleanup -- --booking-id UUID --execute`. El helper comprueba la reserva en Upstash y metadatos privados del evento, rechaza cualquier evento no marcado y usa `sendUpdates=none`. Elimina solo ese evento y esa reserva; nunca escanea ni vacía un calendario. Si falla, conservar el UUID para revisar el código de error.

Un 4xx definitivo de Google revierte la reserva pendiente y libera claims. Ante timeout o 5xx después de intentar crear un evento, el resultado puede ser incierto: conservar el mismo UUID y reintentar para buscar el evento determinístico antes de insertar otro. Una confirmación de Google seguida por fallo de Redis también requiere reconciliación. FreeBusy e insert no forman una transacción de Google; un editor externo aún puede ocupar un hueco entre ambas operaciones.

## PRODUCTION

Está bloqueado por código. Google TEST es exclusivamente loopback y utiliza calendarios y destinatarios de prueba. Ninguna credencial en `.env.local` habilita producción. La única autorización para una fase posterior es la frase exacta **APROBADO PRODUCCIÓN**.
